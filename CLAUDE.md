## What this is

AuriNutri — a platform for nutritionists to manage patients, anamnesis, anthropometric
assessments, a food database (TACO + custom foods), and meal plans with automatic macro
calculation. Next.js 14 (App Router) + TypeScript + Tailwind + shadcn/ui, backed by Supabase
(Auth + Postgres + RLS). UI, copy, and identifiers throughout the codebase are in Portuguese
(pt-BR) — match that when adding features.

## Commands

```bash
npm install
npm run dev            # http://localhost:3000, redirects to /login
npm run build
npm run start
npm run lint
npm run test:e2e        # Playwright E2E (needs SUPABASE_SERVICE_ROLE_KEY, see e2e/README.md)
npm run import:taco     # imports TACO food data — needs SUPABASE_SERVICE_ROLE_KEY (see below)
```

`npm test` runs the Vitest unit tests; `npm run test:e2e` runs the Playwright E2E suite in `e2e/`.

### Environment

Copy `.env.local.example` to `.env.local` and fill in a Supabase project's URL + anon key
(`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_SITE_URL`).
`SUPABASE_SERVICE_ROLE_KEY` is only needed locally for `npm run import:taco` (it bypasses RLS
to write global/TACO foods) — never used by the deployed app, never exposed to the browser.

Env vars must be read as `process.env.LITERAL_NAME` (not `process.env[name]`) — Next.js only
inlines `NEXT_PUBLIC_*` vars into the browser bundle on a static access; dynamic access yields
`undefined` client-side. See the `requiredEnv` helper duplicated in each of the three Supabase
client files.

### Database setup

Run the SQL files in `supabase/migrations/` in order via the Supabase SQL Editor:
`0001_init.sql` (core schema: patients, anamnesis, assessments, foods, meal plans + RLS),
then `0002_taco_foods.sql` (TACO/global foods, micronutrients, historical meal-item snapshot).
There is no Supabase CLI/migration-runner wired up — migrations are applied by hand.

## Architecture

### Supabase clients — three, not interchangeable

- `src/lib/supabase/client.ts` — browser client for Client Components.
- `src/lib/supabase/server.ts` — server client for Server Components/Actions/Route Handlers;
  reads/writes the session via `next/headers` cookies.
- `src/lib/supabase/middleware.ts` — used by `src/middleware.ts` (must live in `src/`, not the repo root — Next.js silently ignores a root one when `src/app` is used; same for `src/instrumentation.ts`) to refresh the session on every
  request and enforce route protection: unauthenticated users get redirected to `/login`
  (preserving `?redirectTo=`), authenticated users get bounced off `/login`/`/cadastro`.
  Public routes are hardcoded in `PUBLIC_ROUTES`.

None of these pass the `Database` generic to the Supabase client. `database.types.ts` is
hand-written (not generated by the Supabase CLI), and passing it as the generic makes
`supabase-js`'s query parser infer partial `select()`s as `never`, breaking the build. Instead,
domain types (`Patient`, `Food`, `MealPlan`, ...) are applied explicitly per-query via
`.returns<T>()` / `.single<T>()`. Keep doing this — don't "fix" it by wiring up the generic.

### Server Actions, not API routes

Data mutations live in `src/lib/actions/*.ts` (`"use server"`), one file per domain area
(`patients`, `clinical`, `foods`, `meal-plans`, `meals`, `meal-items`). Each action: parses
input with a Zod schema from `src/lib/validations/`, gets the Supabase server client, checks
`auth.getUser()` where the row needs an explicit `user_id`, does the query, then
`revalidatePath(...)` the affected routes and either `redirect()` or return an `ActionResult`
(`{ success, message? }`). Follow this shape for new actions rather than introducing Route
Handlers for CRUD.

### Row Level Security is the authorization model

Every table has RLS keyed on `auth.uid() = user_id`. There is no app-level permission check
beyond that — Server Actions rely on Postgres to reject cross-tenant access. TACO/global foods
(`foods.is_global = true`, `user_id = null`) are readable by everyone but writable only via the
service-role key (i.e. only by `scripts/import-taco/import.mjs`), never by nutritionists through
the app. When adding a table or action, add the matching RLS policy in a new migration — don't
rely on query-level filtering alone.

### Nutritional snapshot — meal items never recompute from live food data

`meal_items` stores a full copy of the food's nutrition (`nome_alimento`, `fonte_alimento`,
`calorias_kcal`, `proteinas_g`, ...) at the moment it's added to a meal, plus `food_id` kept only
as a traceability pointer (nullable — the source food may later be edited or deleted). All macro
math in `src/lib/nutrition.ts` (`calculateMealItemMacros`, `calculateMealTotals`,
`calculatePlanTotals`) operates on this snapshot, never on a live join to `foods`. This is
deliberate: editing or deleting a food must never change a meal plan that already used it. When
touching meal-item creation, always copy the food's current values in; never read them back out
live.

`valores_especiais` (a `{column: reason}` map) preserves *why* a nutrient is null — `"traco"`
(trace amount), `"nao_analisado"` (not analyzed), or `"nao_informado"` (not reported) — sourced
from the TACO table. These are never coerced to `0` in the data; `0` is only used transiently
when summing macros (`calculateFoodMacros`/`calculateMealItemMacros` treat missing as 0 for the
sum, but the underlying `foods`/`meal_items` column stays `null`). `formatNutrientValue` in
`nutrition.ts` renders the three cases distinctly ("traço" / "não analisado" / "—").

### Source attribution (TACO vs. custom)

Every food and meal-item snapshot carries `fonte` / `fonte_alimento` (`"taco" | "personalizado"`).
`buildFonteFooter()` in `nutrition.ts` generates the correct attribution footnote for a plan
based on which sources its items actually use — never attributes a custom food to TACO. This
same function is meant to back a future PDF export.

### Routing structure

- `src/app/(auth)/` — login, cadastro, esqueci-senha, redefinir-senha (own layout).
- `src/app/(app)/` — the logged-in area: dashboard, pacientes, alimentos, planos, fontes.
- `src/app/auth/callback/` — exchanges the email-link code for a session.

Both route groups are protected/redirected centrally by `src/middleware.ts`; `(app)/layout.tsx` also redirects to `/login` as a second line of defense.

## Deployment

Deploys to Netlify (`https://aurinutri-app.netlify.app`, AuriNutri's own Netlify account) via `@netlify/plugin-nextjs` (`netlify.toml`, Node 22); `next.config.mjs` force-includes `pdfkit/js/**` in the function bundle via `outputFileTracingIncludes` — without it every PDF-generating page crashes the function in production; Server Components, Server
Actions, Route Handlers, and `middleware.ts` are converted to Netlify Functions/Edge Functions
automatically. Migrations and `npm run import:taco` are never run as part of deploy — they're
manual, local/Supabase-SQL-Editor-only steps.
